# Exact Reader intent observations

`ChapterIntentReadSet` is the exact wanted intent, source reference and portable render-plan reference read atomically by the Reader's `ChapterDemandOutbox`. An incomplete legacy/source-only entry or a cancelled intent cannot produce it. Reader acknowledgements do not change wanted state; cancellation, re-request or source/plan attachment changes the intent revision and invalidates an older read set. Existing journal encodings are unchanged by this component.

The SDK publishes a bounded, canonical, immutable V1 envelope through `ChapterLocalIntentSnapshot.publishCurrent`. It binds the actual Reader account, requesting device, request/render identity, exact intent revision and both content references. The envelope contains no source text, paths, producer epoch or private voice data. Publication uses the existing descriptor-bound immutable blob helper, with actual staged readback, no-replace commit, synchronization and exact existing-record reconciliation. The payload cap is 128 KiB. Owned detached file operations cancel and join.

The publisher rechecks the Reader's current intent before commit and after completion. A late cancellation can leave complete immutable evidence while returning no publication receipt. This evidence must never be treated as current work merely because its file exists, is newest in a directory or has a matching hash.

`ChapterIntentAuthority` is a required, read-only current-state boundary. `ChapterReaderIntentAuthority` executes inside the Reader owner and checks its own captured account epoch before and after the atomic outbox observation. It exposes no mutations or journal paths. The future signed host must authenticate the Reader IPC endpoint; a cached snapshot or always-true implementation is not a valid provider. The included adapter and tests are in-process components, not an IPC or service implementation.

The receiver supplies its own fresh account session/gate, expected exact request and requesting device. `receive` checks the canonical snapshot and asks the Reader authority whether the complete read set is still current, then checks the receiver epoch again. Missing, closed, failed or offline authority fails closed. `requireCurrent` repeats that check at subsequent work boundaries. A producer epoch never becomes the receiver epoch.

These checks are observations, not locks or leases. A cancellation can occur after a successful observation. The future worker must revalidate before model work, between bounded work units and before publication, and must use the later generation/claim transaction to fence acceptance. This component does not start a renderer, create a claim, mark audio ready, confirm CloudKit demand or activate a backend.

The separate opt-in authority described in `CHAPTER-DURABLE-INTENT-AUTHORITY.md` now provides a journal-bound filesystem observation channel. It blocks before mutations, recovers from the authoritative journal, pins publication ownership and rejects old/plain writers. A simple pointer published after a journal save would still be unsafe: an old wanted pointer could survive a newer cancellation. The live Reader adapter remains available for in-process checks; offline observation requires the explicitly configured durable authority. Neither adapter grants a worker claim or atomic output acceptance. The companion never opens the Reader's mutable outbox, and autonomous background rendering still requires the remaining orchestration and acceptance fences.

Validation covers complete/incomplete intent, exact restart observations, idempotent immutable publication, stale cancel/re-request, mismatched device/request/options references, cancellation before and after commit, Reader A→A and Worker epoch changes, and unavailable authority. Fixtures use synthetic references and metadata; they perform no model inference, signed-process exchange, CloudKit or user-journal migration. Aggregate quota/retention, authenticated IPC, durable authority, claims/checkpoints, service/catalog and actual generation/playback remain pending.
