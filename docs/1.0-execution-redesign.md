# LibroxTTS 1.0 — execution redesign proposal

This replaces the incremental priorities in the 2026-11-12 review after the user's
request for a much larger 1.0 improvement. This document is a proposal, not an
implementation, performance result or authorization to publish another release.
Baseline: published 0.9.0, `07fcf437004027f58ad8bb16de7877d0ee74a9a8`.

## Outcome

Build a new internal execution core behind the existing public contracts. Make
preparation, inference state and resource ownership explicit enough to eliminate
whole classes of repeated work. Small allocation fixes and qualification are
supporting work, not the headline of 1.0.

Ambitious engineering targets, not forecasts or measured gains:

| Workload | Target to investigate |
|---|---|
| A nominated, representative sustained Max workload on its shipping route | 2x synthesis throughput |
| True cold startup on a nominated device, including all preparation | 50% lower time to first accepted audio |
| Contextual/number-heavy/dictionary-heavy long-text planning outside 0.9's fast domain | 10x lower planning time |
| Cold English dictionary construction | 5x lower time and reduced transient allocations |
| A demonstrated duplication/state-heavy memory workload | 30% lower peak process memory |

Do not combine these ratios or imply they apply to every backend, language or
voice. Name and fix workloads before experimentation, include ordinary short
controls, and show p50/p95 and total wall time. Count setup and compilation costs;
preview warming cannot be used to disguise cold latency. Separate host playback
latency from generation latency. Baseline stage attribution must establish whether
a proposed change has enough leverage to meet the target. If host overhead is a
small fraction, input-buffer cleanup cannot plausibly double total throughput.

## A. One internal representation for text preparation

Current evidence: TextNativeNarrationPlanner still normalizes every growing prefix
outside its conservative PlainNarrationBudget domain. Numbers, matching custom
readings and contextual rules fall back to that path. Increasing the list of safe
punctuation cases is not the larger architectural solution.

Build an internal prepared-text representation with original UTF-16 source mapping,
normalization dependencies, stable and context-sensitive spans, and tokenizer
budget information. Incrementally recompute affected spans as the prefix grows,
without rerunning all rules over the whole prefix. Compile dictionary matching
structures once per immutable lexicon. Retain Apple sentence segmentation and
existing public input limits and split-selection order.

This is not permission to normalize the full sentence once and slice the result:
a prefix can change a number reading or rule context. The incremental evaluator
must reproduce the old output at each tested endpoint, including the first failing
prefix, not assume monotonicity. Keep the original implementation as an oracle and
fallback for unproven productions. Exercise randomized Unicode, punctuation,
lexicon overlap and all supported language pipelines. Final plans, phonemes,
source ranges, errors and synthesis text must match exactly.

In the same preparation layer, prototype indexed/typed bundled English dictionary
storage. Preserve existing casing, null/variant handling, supplement precedence,
resource errors and weak ownership. Do not silently fix old dictionary semantics.

## B. Separate immutable execution assets from render state

Introduce internal ownership boundaries for:

- Verified source identity and parsed immutable metadata/weight storage.
- Backend-specific execution plans: graph handles, validated shapes, static inputs
  and schedules, with explicit configuration identity.
- Render state: RNG, attention caches, codec history, continuation, counters,
  cancellation and callback delivery.

Use bounded sharing only for resources proven immutable and safe to share. Live
clients hold leases; last-owner release/unload and memory-pressure behavior remain
compatible. Concurrent load coalescing may save duplicate work, but must preserve
each caller's cancellation, validation, error and RNG semantics. Sharing an already
initialized model must not skip random draws that 0.9 consumes on cold creation.

Do not share mutable model instances, RNG streams, stateful prediction objects,
callback buffers or exposed MLXArray references. Some mapped file pages may already
be shared by the OS: measure actual duplication before attributing memory savings
to a registry. Existing single-renderer reuse already works and is not a new gain.
Retain per-render asset checks where the old API observes file changes; a cached
verification result is not automatically valid because path/mtime is unchanged.

This boundary enables the new fast path while existing public direct-model APIs
retain their behavior. Avoid duplicating inference mathematics: share narrowly
parameterized computational primitives, with compatible adapters for old public
state and separate private state. Do not move or remove public types/products.

## C. Redesign the inference execution path

The engine-owned path should minimize reconstruction, copying and synchronization
between frames, with bounded state and allocation lifetimes.

MLX: integrate capacity-managed attention state into the private execution path,
not KVCacheSimple. The 0.9 experiment passed sixteen model-audio cases but failed
public reference semantics; that establishes a reason to redesign the boundary,
not proof of speed. Preserve public state-returned references and direct-model
operations. Extend exact tests through capacity growth, continuation, cancellation,
all sampler counts and long runs before paired CPU/GPU performance measurements.

Core ML: profile transformer, flow and codec work separately from host transport.
Keep tensors in compatible backend-owned form between predictions where lifetime
rules allow, materializing caller-owned PCM at the existing delivery boundary.
Use explicit input workspaces and execution plans, preserving scalar conversion
expressions, operation order, random draws, specialized 4/8-step behavior and
callback/checkpoint order. The default four-step graph does not incur all generic
step-array costs, so optimizing those alone cannot justify a default-path claim.

If repeated KV input/output transport dominates, investigate a separate stateful
Core ML representation. Apple's state facilities can remove explicit cache I/O,
but this is a high-risk representation experiment: identical weights do not prove
identical arithmetic or audio. It must preserve existing pinned assets and their
supported load/receipt contracts, or stay outside the strict drop-in candidate.
Never silently replace model packs or compiler generations with incompatible ones.

Similarly, MLX graph compilation/fusion is research until exactness is demonstrated;
compiler optimization can alter evaluation and rounding. Do not enable it globally,
upgrade dependencies casually, or accept a numerical tolerance to get a speed win.

## D. Reduce the Core ML route's incidental MLX work

The current Core ML engine uses MLX for random generation and safetensor voice-state
loading, while also depending on PocketTTSMLX for shared model/text definitions.
Investigate native preparation and an exact-compatible RNG implementation to remove
unnecessary MLX execution from this route. Test cold initialization, each RNG draw,
clamping/scaling, sampling options, failure/reseed/reload and final PCM.

Distinguish runtime decoupling from binary dependency removal. Public PocketTTSMLX
products and exposed MLX types must remain available. The current LibroxTTS package
graph links them; merely moving imports does not make existing iOS consumers MLX-free.
A lean optional product is an additive packaging proposal, not a mandatory migration
or an automatic win for old clients. Do not make package-size claims without linker
maps and actual client artifacts. Defer this track if exact RNG or package contracts
cannot be retained without excessive duplicate implementation.

## Compatibility proof and delivery

Every optimization is compared with 0.9 under identical backend/device/OS/compiler,
asset bytes, seeds and request sequences. Preserve exact samples, frames and events;
all old public declarations, persisted data, source ranges, defaults, error precedence,
backpressure, cancellation, model retirement, asset and prepared-audio identities.
The facade is not the whole contract: directly exposed engine/model/cache types count.

Qualification remains mandatory but does not constitute the main performance claim.
Run actual process-exit recovery tests and sustained device workloads, broader model/
language coverage, cold/warm paired trials, memory-pressure and cancellation tests.
Keep baseline fixtures immutable. No cross-backend or cross-OS bit-identity claim.

Recommended execution order:

1. Establish stage-cost and memory attribution on representative 0.9 workloads;
   select performance targets whose dominant costs this architecture can address.
2. Implement the prepared-text representation and dictionary prototype, with
   exhaustive/differential prefix and pronunciation gates.
3. Establish private execution-asset/render-state boundaries and exact parity.
4. Run the private MLX cache and Core ML execution-plan experiments; adopt only
   exact, measured improvements. Investigate stateful representations only if the
   measured ceiling of the simpler path is insufficient.
5. Investigate Core ML/MLX runtime decoupling independently; report size/startup
   separately and retain the old public products.
6. Complete the release qualification matrix and publish a workload-specific
   before/after scorecard. Do not call housekeeping alone a huge 1.0 improvement.
